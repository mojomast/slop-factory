The ideas

Six pieces, one factory

Each one works on its own. Together they make a community that ships faster than any one of us.

Umbrella

Slop Factory

What

The umbrella over everything below, plus a public contributors page showing each person's merges, reviews and compute given.

How

The board, pooled workers, shared inference and peer review feed one public ledger. Stars and follows come from people who actually worked together.

Exists in rizzstack

Orbit's board and collab chat, bundlebees contracts and hyvv sandboxes already do this for one person.

01

Shared inference

What

A token router so members who lack inference can use what others choose to share.

How

A router like Bifrost issues each member a virtual key with spend caps, rate limits and per-person usage logs. Donors fund a pay-as-you-go pool or bring their own keys.

Exists in rizzstack

Bifrost is already the chosen router for Orbit.

02

Shared sandboxed workers

What

Resource-strapped members borrow worker slots from those with spare capacity.

How

Hosts lend a few slots to approved repos. Code runs only in a sandbox with a model-endpoint-only network, no credentials inside, and an auto-kill timeout. Hosts can pull slots back any time.

Exists in rizzstack

hyvv runs sandboxed bees (2 cores, 4 GB each) behind an allow-list.

03

Group kanban

What

One board where members commit workers or inference to move a project forward.

How

Every card is an ACDD/TDD contract. Claim a card, attach compute, and merge only with passing evidence. The board records who contributed what.

Exists in rizzstack

The workflow contract format and Orbit's board and chat.

04

Clanker code review

What

Request a review and another member's agent picks it up.

How

A Hermes plugin runs lint and tests in that member's own sandbox, then posts one advisory summary comment. A human decides whether to merge.

Exists in rizzstack

slop-lint, plus a fork-safe PR summary comment workflow.

05

Community starring skill

What

An agent skill that stars and follows the community's repos and people.

How

It reads the shared community list, acts only on entries from it, runs once a day, and shows a dry-run preview first. It's community-based, not a star train.

Exists in rizzstack

Agent skills and scheduled routines.

Straight talk

rizzstack is a one-person stack. You don't need it.

Today, one developer uses rizzstack: the sandboxed workers, the contract board, the dispatch and review plumbing. The pitch is to open pieces of it up, not to ask anyone to switch tools. Everything below plugs into what you already use: your editor, your agent, your GitHub repos.

Fits how you already work

Integration surfaces

Each surface is small and optional. Pick one, or none. All of these are proposed unless marked as existing.

Surface A

GitHub issue + label

Add a label like factory:review or factory:build to an issue or PR in your own repo to request work. No new tool for you.

Surface B

OpenAI-compatible endpoint

A token router speaks the standard chat-completions API. Anything that lets you set a base URL and key can use it: Hermes, OpenCode, Claude Code, Cursor, Aider, Continue, or your own scripts. One key per person, with caps.

Surface C

Lend-a-slot worker

A small container you choose to run. It offers a few CPU slots to the pool, with caps you set and a sandbox around every job. Stop the container and you're out.

Surface D

Hermes plugin / skill

For people on Hermes: request a review, check the board and see your ledger from inside your agent. Hermes plugins are the format rizzstack's own plugins already use.

Surface E

GitHub Action

Posts one advisory summary comment on a PR with lint, tests and the review result. Built on the fork-safe PR comment pattern that already exists.

Surface F

MCP server for the board

Lets any MCP-capable agent list cards, claim one and attach evidence. Your agent talks to the board without you leaving your workflow.

Reviews on yours and access to shared inference.

You give

Nothing required. Reviews and spare slots if you want credit.

You get

A fallback model pool and background workers for long tasks.

A day

You write code as usual. When you hit a rate limit, your tool switches to the shared endpoint. For a big refactor, you file a card and a pooled worker picks it up while you move on.

I just use GitHub

Add the proposed Action file to a repo and create the labels.

You give

A label on issues you'd like help with.

You get

An advisory review comment on every labeled PR.

A day

You open a PR and add factory:review. Later a single summary comment appears. You read it, fix what matters, and merge it yourself.

I have spare compute

Set up (~10 min)

Run the proposed worker container. Set max slots, hours and which repos you trust.

You give

Sandboxed CPU time.

You get

Ledger credit you can spend on tokens or reviews.

A day

The worker sits idle. A trusted repo's job arrives, runs with no network beyond the model endpoint and no credentials inside, gets killed on timeout, and returns logs. You see it in your usage page.

I have no budget for inference

Set up (~5 min)

Get a per-person key with a small starter cap.

You give

Reviews, issue triage, docs or testing: work that doesn't need tokens.

You get

Tokens from a donor-funded pool.

A day

You review two PRs, earn credit, and spend it on a day of coding. The cap stops anyone from overspending.

Fairness

Contribution ledger and trust levels

A simple give/get record, so sharing stays fair and nobody gets quietly drained.

Give / get

The ledger tracks three units: compute minutes (slots lent or used), tokens (through the router) and reviews (given and received). Credit earned in one unit can be spent in another at rates the group agrees on. Balances are visible to everyone, and nobody has to go positive to participate.

Trust levels (proposed)

LevelWhat it allows
NewUse the router with a small cap. Their code never runs on your worker.
KnownTheir jobs can run on workers whose owners opt in, in the sandbox.
TrustedLarger caps, and they can request reviews from the pool.

You decide which level may use your slots. Trust moves up through merged work and reviews, and it can be revoked.

End to end

One card, from request to credit

The target flow. Humans stay in the loop at the merge step.

  1. 1. FileA dev files a card, or labels an issue.
  2. 2. ClaimA member or an agent claims it.
  3. 3. RunA pooled worker runs it in a sandbox, using the shared router.
  4. 4. EvidenceTests and results attach to the card.
  5. 5. ReviewAnother member's clanker posts an advisory comment.
  6. 6. MergeA human reads it and merges, or doesn't.
  7. 7. CreditThe ledger credits compute, tokens and review.

FAQ

Questions you should ask

Do I need rizzstack?

No. rizzstack is the author's own stack. You use an endpoint, a label, a plugin or an Action, whichever fits.

Is my code safe?

Your code only runs on workers whose owners opted in and trust you. Jobs run in sandboxes with no credentials and restricted networking. If a check fails, the job doesn't run. Don't put secrets in anything you share. Treat this as a design goal, since it isn't built yet.

What does it cost?

Nothing to join. Inference comes from pay-as-you-go keys that people donate or bring, with caps. We won't share a single-person subscription across people, because that breaks most providers' terms.

What if I leave?

Revoke your key, stop your worker container, and your repos keep working as plain GitHub repos. Your ledger history can be exported.

Can I limit what I share?

Yes. You set slots, hours, token caps, which repos and which trust level can use them. Sharing nothing and just using the review comments is fine too.

Principles

Safe and fair by design

Sharing compute only works if nobody gets burned.

  • Sandboxed. Borrowed workers never see credentials or the open network.
  • Fail-closed. If a check is missing or unclear, the answer is no.
  • Opt-in. Nobody's compute or keys are used unless they choose.
  • Caps you control. Each donor sets limits and can revoke at any time.
  • Humans merge. Agent reviews are advisory; people approve.
  • No ToS-breaking. We never share a single-person subscription. We use pay-as-you-go or per-person keys.
Roadmap

Start small, then pool

Small, useful, and visible first. Trust and budget rules come before shared compute.

  1. Phase 1Clanker review + starring skill. Both work right away and show something real.
  2. Phase 2Group kanban + contributors page. Contract cards and a public ledger.
  3. Phase 3Shared workers and inference. Once trust, caps and budget rules are agreed.
